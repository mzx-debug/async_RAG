# 异步 RAG 流水线调度器技术报告

---

## 一、问题背景与动机

### 1.1 资源受限环境下的 RAG 挑战

RAG（检索增强生成）推理包含三个计算密集阶段：**嵌入（Embedding）**、**检索（Retrieval）** 和 **生成（Generation）**。在资源受限的边缘 GPU 环境（如 4–16 GB VRAM）下，存在两个核心矛盾：

1. **GPU 显存容量有限**：vLLM 生成模型的 KV Cache 通常占用 60–80% 的显存，剩余空间不足以同时容纳 FAISS GPU 索引（~~1.85 GB）和嵌入模型权重（~~0.4 GB）。
2. **三阶段相互竞争**：嵌入（可 CPU/GPU）、检索（可 CPU/GPU）、生成（必须 GPU）三个阶段都需要调度决策。

因此，调度器的目标是：**在 GPU 资源受限条件下，通过动态选择每个阶段运行的设备（CPU 或 GPU）和 batch size，最小化每个查询的端到端延迟（wall-clock time per query）**。

### 1.2 调度粒度的两个维度


| 维度 | 候选值 | 数量 |
| ---------------- | ----- | --------------------------------------------------- |
| **Action（设备配置）** | (xE, xR) 组合：xE ∈ {0=CPU, 1=GPU}，xR ∈ {0=CPU, 1=GPU} | 4 种 |
| **Batch Size** | 任意整数 B ∈ [1, min(pending_count, B_max(action))] | 动态，上界由显存约束决定 |


组合后调度器只需比较 **4 个 action 各对应 1 个最优 B***，无需遍历 batch size 候选。

## 二、系统架构

### 2.1 三线程流水线

```
┌──────────────┐    q_er     ┌──────────────┐    q_rg     ┌──────────────┐
│ embed_worker │ ──────────→ │ retrieval_   │ ──────────→ │ generation_   │
│              │             │ worker       │             │ worker       │
│  (CPU 或 GPU) │             │  (CPU 或 GPU) │             │  (GPU/vLLM)  │
└──────────────┘             └──────────────┘             └──────────────┘
       ↑                                                            │
       │              dispatch_cv                                    │
       └─────────────────── main thread ────────────────────────────┘
                              ↑
                        scheduler.next_dispatch()
```

**关键设计**：embed_worker 每次干完一个 batch 后停下来等主线程下一次调度。这种**半并发**模型确保 action 可以随时切换，而无需重启 worker。

### 2.2 三阶段完全并行模型

Emb、Ret、Gen 三个阶段**完全并行运行**，其时间取最大值：

```
wall_q = max(emb + xfer_EtoR, ret + xfer_RtoG, gen) + queue_penalty
```

其中：

- `xfer_EtoR = I(xE≠xR) × K[xE,xR] × L`：Emb→Ret 传输时间（加在 Emb 上），仅当两阶段设备不同时生效
- `xfer_RtoG = I(xR≠1) × K[xR,1] × L`：Ret→Gen 传输时间（加在 Ret 上），仅当 xR≠1 时生效
- `queue_penalty`：调度开销（固定常数）

## 三、成本模型

### 3.1 各阶段成本公式（第一性原理推导）

**嵌入**（Embedding）：固定开销 + per-token 成本

```
emb_q = e[xE] × L + oh_e[xE] / B
```

其中 e[xE] 是单位 token 成本，oh_e[xE] 是固定开销（启动延迟），除以 batch size B 是因为固定开销在 batch 内被均摊。

**检索**（Retrieval）：

```
ret_q = r[xR] + oh_r[xR] / B
```

FAISS 检索时间近似 per-query 固定成本（O(1) flat search）加上固定开销均摊。

**生成**（Generation）：vLLM continuous batching 下的预填充（prefill）开销均摊

```
gen_q = gen_per_token × avg_output_tokens + gen_base / B
```

- `gen_per_token`（ms/token）：解码阶段每生成一个 token 的时间
- `gen_base`（ms）：预填充的固定开销（与 batch size 无关），在每个查询上均摊为 `gen_base / B`
- `avg_output_tokens`：本次预测的平均输出长度（EMA 自适应跟踪）

### 3.2 完整模型

```
wall_q = max(
    e[xE] × L + oh_e[xE] / B + I(xE≠xR) × K[xE,xR] × L,
    r[xR] + oh_r[xR] / B + I(xR≠1) × K[xR,1] × L,
    gen_per_token × avg_output + gen_base / B
) + queue_penalty
```

### 3.3 默认参数（Qwen2.5-1.5B-Instruct 实测）


| 参数                  | 默认值             | 说明                                        |
| ------------------- | --------------- | ----------------------------------------- |
| `e0`（CPU 嵌入速率）      | 0.36 ms/token   | CPU embedding rate                        |
| `e1`（GPU 嵌入速率）      | 0.00 ms/token   | GPU 下 token 计算极快，趋于 0，时间几乎全为固定开销          |
| `oh_e0`（CPU 嵌入固定开销） | 2.71 ms         | CPU embedding 启动延迟                        |
| `oh_e1`（GPU 嵌入固定开销） | 4.87 ms         | GPU embedding 启动延迟（比 CPU 更高，因涉及 CUDA 同步等） |
| `r0`（CPU 检索边际成本）    | 0.20 ms/q       | 对于固定FAISS索引，O(1) 近似                       |
| `r1`（GPU 检索边际成本）    | 0.00 ms/q       | GPU 下检索极快，趋于 0，时间几乎全为固定开销                 |
| `oh_r0`（CPU 检索固定开销） | 1.36 ms         | CPU 索引加载/初始化开销均摊                          |
| `oh_r1`（GPU 检索固定开销） | 1.50 ms         | GPU 索引加载/初始化开销均摊                          |
| `gen_per_token`     | 0.2135 ms/token | **实测**                                    |
| `gen_base`          | 1109 ms         | **实测**（prefill 固定开销）                      |
| `avg_output`        | 120 tokens      | EMA 自适应                                   |
| `queue_penalty`     | 0.23 ms/q       | **实测**                                    |
| `K[(0,1)]`          | 0.55 ms/token   | CPU→GPU 传输速率                              |
| `K[(1,0)]`          | 0.16 ms/token   | GPU→CPU 传输速率                              |


**参数来源说明**：这些参数通过 `measure_gpu_costs.py` 在 RTX 4090 上实测得到（batch size ∈ {1, 4, 8}），并通过 `validate_model.py` 在真实异步流水线场景中验证了预测误差。

### 3.4 为什么 gen_base / B 很重要

vLLM continuous batching 下，每个 batch 的预填充开销是固定的 1109 ms，与 batch size 无关。因此 batch 越大，每个查询分摊的预填充成本越低：


| Batch Size | gen_base / B（ms/q） | gen_per_token × 120（ms/q） | gen_q 总计（ms/q） |
| ---------- | ------------------ | ------------------------- | -------------- |
| B=1        | 1109.0             | 25.6                      | 1134.6         |
| B=8        | 138.6              | 25.6                      | 164.2          |
| B=64       | 17.3               | 25.6                      | 42.9           |
| B=256      | 4.3                | 25.6                      | 29.9           |


这就是**更大的 batch 更快**的原因——但不能无限大，受 GPU 显存限制。

### 3.5 长 Query 的分块处理

**async_v2 模式下**，超过 64 tokens 的 query 会被**滑动窗口分块**后统一嵌入：

```
chunk_size = 64 tokens
overlap = 32 tokens（相邻 chunk 之间）
step = 64 - 32 = 32

一个 200 token 的 query → 6 个 chunk：[0:64], [32:96], [64:128], [96:160], [128:192], [160:200]
```

所有 chunk 在**一次 model forward pass** 中完成嵌入，嵌入后对同一 query 的多个 chunk embedding 取**平均**，再归一化。

这保证了长 query 的语义不会因截断而丢失。但当前的成本模型**尚未建模分块开销**——模型中嵌入成本使用的是 query 的原始 token 长度 `L`，没有考虑一个 query 被切分成多个 chunk 后实际产生的额外嵌入计算量。

### 3.6 当前成本模型的局限

1. **未建模分块**：长 query 的实际嵌入成本 ≈ `ceil(L / step) × (e[xE] × chunk_size)`，模型中使用 `e[xE] × L` 会**低估**长 query 的嵌入时间
2. **batch 内长度异质性**：batch 内不同 query 长度不同，但模型用平均长度 `L` 估算，对长度方差大的 batch 误差较大

## 四、贪心调度算法

### 4.1 单调性与解析 B* 决策

成本模型中三项均具有 `a + c / B` 形式，是 B 的**单调递减函数**。单调递减函数族的 pointwise maximum 仍单调递减：

```
∂wall_q/∂B < 0,  ∀B > 0
```

因此对于任意给定的 action，最优 batch size 就是**最大可行 batch size**：

```
B*(action) = min(pending_count, B_max(action), B_backpressure)
```

这消除了 batch size 维度的搜索——调度问题从"4×N 候选枚举"退化为"4 个 action 的比较"。

### 4.2 可行性检查

每次调度前，先确定每个 action 的**最大可行 batch size**：

1. **GPU 显存约束**：`B_max(action) = ResourceTracker.max_batch_size_for_action(xE, xR)`
2. **待处理队列约束**：`B ≤ pending_count`

可行 batch size 为 `[1, min(pending_count, B_max(action))]`，取整。显存约束通过 `max_batch_size_for_action` 硬上限实现，无需在选择阶段额外筛选。

### 4.3 动作选择

遍历 4 种 action，各取最大可行 B = min(pending_count, B_max)，预测 wall_q，取最小者：

```python
def next_dispatch(self, gpu_available, gpu_mem_gb, q_er_len, q_rg_len, ...):
    pending_count = len(self._pending_queries)
    if pending_count == 0:
        return None

    best_score = float('inf')
    best_batch_size = 0
    best_action = (0, 0)

    for xE, xR in [(0,0), (0,1), (1,0), (1,1)]:
        if not self._feasible_actions_ema.get((xE, xR), True):
            continue

        # 单调性：最大可行 batch 即最优 batch
        B_mem = self.resource_tracker.max_batch_size_for_action(xE, xR)
        B = min(pending_count, B_mem)

        if B < 1:
            continue

        # 用成本模型预测 wall_q
        wall_q = self._estimate_wall_time(B, xE, xR, pending_count)

        if wall_q < best_score:
            best_score = wall_q
            best_batch_size = B
            best_action = (xE, xR)

    items = self._pack_batch(best_batch_size)
    return ScheduledMicrobatch(
        query_indices=[...],
        lengths=[...],
        action={"xE": best_action[0], "xR": best_action[1]}
    )
```

### 4.5 调度决策的特点

- **解析决策**：利用成本模型单调性，无需遍历 batch size，每步仅比较 4 个 action
- **显存感知**：ResourceTracker 在运行时动态检查 GPU 显存约束，不依赖静态估算
- **在线自适应**：EMA 在线学习跟踪硬件状态漂移，使调度决策越来越准确
- **轻量级**：每次调度仅 4 次成本估算，远低于调度本身的延迟（~0.23ms queue_penalty）

## 五、EMA 在线学习

### 5.1 为什么需要在线学习

成本模型参数（嵌入速率、检索成本、生成速率）随硬件温度、GPU 利用率、vLLM 内部状态动态变化。离线标定只能给出一个初始值，运行时的在线学习可以跟踪这些变化。

### 5.2 EMA 公式

```
new_value = α × observed + (1 - α) × old_value
```

其中 `α = 0.25`（可配置），意味着每次更新将 25% 的权重给新观测，75% 保留历史值。

### 5.3 关键设计：预更新值冻结

所有 EMA 更新前，先将**当前值复制一份作为预更新值**，再进行所有 EMA 写入。这样避免了同一 batch 内不同参数的循环引用（emb 的残差会影响 ret 的估计，ret 的残差又会影响 gen 的估计）。

```python
# 所有 EMA 值在更新前冻结，避免循环引用
prev_gen_per_token = self._gen_per_token_ema
prev_gen_base = self._gen_base_ema
prev_avg_out = self._avg_output_tokens_ema
prev_e0 = self._emb_rate_ema.get(0, 0.36)
# ... 其余参数同理
```

### 5.4 分步骤拟合

每个 batch 结束后，按以下顺序更新参数：

#### Step 1 — 嵌入拟合

收集 (L, B, emb_ms_total) 数据点，用指数加权线性回归同时拟合速率和固定开销：

```
emb_total = e_base × (L × B) + overhead
```

- 1 个数据点时：直接解析求解
- ≥2 个数据点时：指数加权线性回归（近期数据权重更大）
- 超过 20 个数据点后丢弃最老的

#### Step 2 — 检索拟合

对称于嵌入，用 (B, ret_ms_total) 数据点拟合：

```
ret_total = r_base × B + overhead
```

#### Step 3 — 生成参数拟合

- **per-token 率**：`gpt_obs = gen_ms_total / total_output_tokens`
- **平均输出长度**：`avg_out_obs = total_output_tokens / B`
- **gen_base（prefill 固定开销）**：从总时间剥离 per-token 成本后反解
  ```
  gen_base_obs = (gen_ms_total - prev_gen_per_token × total_output_tokens) / B
  # 加权：输出越长越置信
  token_weight = min(1.0, total_output_tokens / 200.0)
  b_factor = token_weight × α
  _gen_base_ema = b_factor × gen_base_obs + (1 - b_factor) × prev_gen_base
  ```

#### Step 4 — 传输速率 K 和 Queue 拟合

从 wall_time 的残差反推：

```
wall_q = max(emb_with_xfer, ret_with_xfer, gen_q) + queue_penalty
queue_obs = wall_q - max(emb_with_xfer, ret_with_xfer, gen_q)
```

只有在**慢阶段**是 emb 或 ret 时（gen 不主导时），残差才被用于拟合对应的传输速率 K。

### 5.5 EMA 的置信度机制

- **gen_base 的置信度随输出 token 数增长**：短输出（< 200 token）的 batch 对 gen_base 的更新权重较小，因为短输出的 gen_base_obs 方差较大
- **指数加权**：最近 20 个数据点的权重呈指数衰减，确保 EMA 能跟踪参数漂移而不被早期数据淹没

## 六、显存感知调度

### 6.1 ResourceTracker

ResourceTracker 实时监控 GPU 显存：

```python
def max_batch_size_for_action(self, xE: int, xR: int) -> int:
    required = self._estimate_model_mem(xE, xR)
    available = torch.cuda.get_device_properties(0).total_memory - self._used_mem
    return int(available / required)
```

### 6.2 显存压力分级（分类器已实现，调度应用待开发）

ResourceTracker 实时将剩余显存划分为三级：

| 压力等级 | 剩余显存 | 分类结果 |
| -------------- | ---- | --------------------- |
| **低**（> 10 GB） | 充足 | `pressure_level = "low"` |
| **中**（4–10 GB） | 紧张 | `pressure_level = "medium"` |
| **高**（< 4 GB）  | 极紧张 | `pressure_level = "high"` |

分类器已在 `ResourceTracker.pressure_level()` 中实现，`_compute_overlap_potential()` 方法中也预留了按压力等级调整 overlap 评分的逻辑（高分 = 更推荐该 action）。但当前版本中 `_compute_overlap_potential` **尚未被调度主循环调用**，因此压力分级暂未实际影响调度决策。实际的显存约束仅通过 `max_batch_size_for_action` 和 `_action_feasible` 的硬上限实现。


### 6.3 GPU 常驻索引

当选择 (xE=1, xR=1) 且 GPU 可用时，设置 `keep_gpu_resident_er=True`，将 FAISS GPU 索引保持在显存中，避免下次使用时重新加载（~300 ms 开销）。

## 八、已知局限与未来工作

### 8.1 当前局限

1. **未建模分块嵌入开销**：async_v2 对长 query（> 64 tokens）使用滑动窗口分块嵌入（step=32），但成本模型使用原始长度 `L` 估算，会低估长 query 的嵌入成本
2. **batch 内长度异质性**：batch 内不同 query 长度不同，但模型用平均长度 `L` 估算，对长度方差大的 batch 误差较大
3. **压力分级尚未联调**：`ResourceTracker.pressure_level()` 和 `_compute_overlap_potential()` 已实现但未被调度主循环调用，显存约束仅靠硬上限（batch size 上限）实现
4. **gen_per_token 对 gpu_util 敏感**：标定值在 gpu=0.8 时偏低（实测约 0.15 vs 标定 0.21），在 gpu=0.3 时偏高（实测约 0.38）
5. **(1,0)/(1,1) 参数未从数据拟合**：GPU 端嵌入/检索参数全靠初始值，准确性未知

### 8.2 未来方向

1. **建模分块嵌入成本**：将长 query 的 chunk 数量纳入成本模型：`emb_q = e[xE] × ceil(L / step) × chunk_size`
2. **联调压力分级**：将 `_compute_overlap_potential` 接入调度主循环，实现显存压力的软调度
3. **多 gpu_util 自适应**：根据实际 GPU 利用率动态切换 gen_per_token 查表
4. **GPU 端参数实测**：补跑 (1,0)/(1,1) 的实际测量数据
5. **强化学习调度**：用 RL 替代贪心策略，学习考虑未来状态的调度策略
